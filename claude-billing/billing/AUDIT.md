# Аудит биллинга: найденные проблемы, исправления, тесты

> **Статус проверки.** В среде, где выполнялась работа, нет .NET SDK и доступа к сети, поэтому
> `dotnet build` и `dotnet test` **не запускались**. Код и тесты написаны и вычитаны вручную,
> выполнение не подтверждено. Запустите `dotnet build && dotnet test` (нужен Docker для Testcontainers)
> и пришлите вывод, если что-то не соберётся или упадёт.

## 1. Найденные проблемы (в исходной реализации)

| # | Проблема | Последствие |
|---|---|---|
| 1 | Создание платёжной попытки: «проверить ключ → вызвать провайдера → записать». Параллельные запросы с одним `Idempotency-Key` все проходили проверку и все вызывали провайдера; уникальный индекс срабатывал только при записи. | Несколько реальных платежей у провайдера на один логический запрос; «осиротевшие» платежи. |
| 2 | Сбой после вызова провайдера и до записи в БД: у нас нет следа попытки. | Деньги можно получить по платежу, которого мы не знаем; повторный запрос создаёт второй платёж. |
| 3 | Ключ был уникален в рамках счёта, параметры запроса не сравнивались. | Тот же ключ с другой суммой молча возвращал старый результат. |
| 4 | Вызов провайдера без идемпотентного ключа и без таймаута. | Нельзя безопасно повторить вызов; зависший провайдер блокирует запрос. |
| 5 | Повторный `event_id` с другим телом молча принимался как «дубликат». | Подмену или ошибочное событие невозможно обнаружить. |
| 6 | Только платежи на полную сумму счёта, только полный возврат; у счёта не было сумм оплаты/возврата, только статус. | Частичные операции невозможны; нет инварианта «оплачено ≤ счёт». |
| 7 | Лишний платёж на уже оплаченный счёт попадал только в аудит; логика возврата опиралась на `PaidByAttemptId`. | Нет различия «зачтено / не зачтено», нечего сверять и нечем диагностировать. |
| 8 | Отклонённые (`Rejected`) и «мёртвые» (`DeadLetter`) события не попадали в место, пригодное для разбора; ручного возврата события в очередь не было. | Восстановление только прямой правкой БД. |
| 9 | Отмены подписки не существовало; оплата отменённой подписки только писалась в аудит без правила и признака для поддержки. | Неоднозначное поведение. |
| 10 | При недоступной БД ошибка записи сбоя в `catch` выбрасывалась наружу и маскировала исходную причину; необработанные исключения не превращались в 500. | Нестабильный ответ провайдеру, потеря диагностики. |
| 11 | Не было фоновой дочистки попыток, застрявших между «создана у провайдера» и «сохранена». | Потенциальный вечный пробел. |

## 3. Архитектурные решения

- **Идемпотентность платежей — резервирование в БД до сети.** Короткая транзакция вставляет попытку `Creating`; глобальный уникальный индекс по ключу схлопывает конкурентные запросы в одну строку. Затем вызов провайдера без транзакции и блокировок (с таймаутом) с ключом = id попытки, затем условный `UPDATE … WHERE Status='Creating'`. Любой повтор (клиентский, фоновый) вызывает провайдера с тем же ключом и получает тот же платёж. Этого достаточно, чтобы после любого сбоя не возникло второго платежа, при условии, что провайдер соблюдает контракт идемпотентности.
- **Сравнение параметров** — по «сырому» запросу (счёт + запрошенная сумма или «полная»), чтобы корректный повтор после частичной оплаты оставался тем же запросом.
- **Деньги на счёте — суммы, а не флаг.** `PaidMinor ≤ Total`, `RefundedMinor ≤ PaidMinor`; сумма попытки ≤ остатка на момент создания; при подтверждении зачёт только если не превысит остаток, иначе деньги остаются как «излишек» (`AppliedToInvoice=false`) и фиксируются аномалией `SurplusPayment` для ручного возврата.
- **Возвраты** считаются по уникальному `ProviderRefundId`, а не по `event_id`; сумма возвратов по попытке ограничена суммой платежа.
- **Бизнес-правила:** активация — когда счёт оплачен полностью; продление идёт от конца текущего периода (или от «сейчас», если он истёк); частичный возврат подписку сохраняет, полный возврат всей оплаты отменяет подписку и отзывает доступ; отмена пользователем сохраняет доступ до конца оплаченного периода; оплата отменённой подписки остаётся на счёте, но не продлевает её и поднимает аномалию `PaymentForCancelledSubscription`.
- **Конфликт событий:** тело хэшируется; тот же `event_id` с другим телом не применяется, пишется аномалия `EventPayloadConflict`, ответ 409.
- **Транзакционность:** обработка вебхука — одна транзакция с блокировками в порядке событие → попытка → счёт → подписка; ошибка откатывает всё, журнал сбоя пишется отдельной короткой транзакцией и не бросает исключение, если БД недоступна (событие остаётся в очереди). Сеть провайдера в этих транзакциях не используется.
- **Восстановление:** retry с экспоненциальной паузой, `DeadLetter` после `MaxWebhookAttempts` с аномалией, ручной `requeue`, фоновая дочистка попыток `Creating`.

## 4. Тесты

Всего методов-тестов около 70 (с учётом `Theory` строк больше). Ключевые сценарии:

- **Unit:** вычисление статуса счёта (9 случаев), проверка HMAC-подписи (формат, секрет, подмена тела, допуск по времени в обе стороны, разбор повреждённых заголовков без исключений), идемпотентность тестового провайдера, хэш содержимого.
- **Идемпотентность платежей (интеграционные, конкурентные, со сбоями):** 20 параллельных запросов — одна строка и один платёж у провайдера; повтор после оплаты возвращает исходный результат; тот же ключ с другой суммой/счётом — 422; неверные суммы; потеря ответа провайдера после создания; сбой до создания; таймаут провайдера; фоновая дочистка без повторного запроса клиента; конкурентные запросы при сбоях провайдера; отсутствие транзакций и блокировок во время сетевого вызова (`FOR UPDATE NOWAIT` проходит).
- **Повторное зачисление:** один платёж под разными event id (последовательно и параллельно); один event id с другим телом (409, аномалия, состояние не изменилось); идентичная повторная доставка не считается конфликтом; успех после полного возврата; запоздавший `failed`; отклонённые события доступны через админ-API.
- **Частичные платежи и возвраты:** 2×500 ₽ на счёт 1000 ₽ (активация только в конце); повтор подтверждения; параллельные подтверждения с дублями; ограничение остатка; излишек, его пометка и возврат; частичный возврат 200 ₽ дважды; два возврата одновременно; четыре параллельных возврата по 300 ₽ при 1000 ₽ оплаты — применяются ровно три; возврат больше оплаты; накопительный возврат до полного; возврат одного из двух платежей; возврат неактивированной подписки.
- **Подписка:** длительность периода 7/30/365; продление ровно на период тарифа от конца предыдущего; повторные события после продления; два периода одновременно (60 дней, ничего не потеряно) — для активной и для ожидающей подписки; оплата после истечения; оплата отменённой подписки (неактивированной и активной); идемпотентная отмена.
- **Сбои и восстановление:** падение на каждом шаге обработки платежа (`after-lock`, `attempt-updated`, `invoice-updated`, `subscription-updated`) — ничего не применено частично, потом применяется ровно один раз; падение после записи возврата; недоступность БД во время обработки (событие остаётся в очереди) и до сохранения события (500, повторная доставка проходит); 6 параллельных запусков восстановления одного события; dead-letter, аномалия и ручной requeue; восстановление двух сохранённых, но необработанных событий.
- **Целостность:** `AssertInvoiceIntegrityAsync` сверяет с БД суммы счёта с суммой позиций, зачтённых попыток и возвратов, статусы, пределы; почти каждый финансовый тест вызывает её; `GlobalIntegrityTests` проходит по всей БД, включая периоды подписок, выданный доступ и единственность активации.

## 6. Оставшиеся ограничения и риски

- **Главный риск:** код ни разу не компилировался и не запускался. Вероятны опечатки и неверные допущения о поведении EF/Npgsql/TestServer (например, что `ExecuteSqlAsync("SELECT … FOR UPDATE")` берёт блокировку, что необработанное исключение в TestServer превращается в 500 через наше middleware).
- Схема создаётся `EnsureCreated`: она изменилась, старую БД нужно пересоздать; для продакшена нужны миграции EF.
- Корректность п. 1 держится на том, что реальный провайдер поддерживает идемпотентные ключи. Если нет, нужна сверка по метаданным платежа.
- Незавершённые платежи не резервируют остаток счёта: два параллельных платежа на весь остаток возможны; второй при подтверждении станет излишком и потребует ручного возврата.
- Возврат платежа за продление отменяет подписку целиком (период не откатывается по отдельности).
- Правило «частичный возврат сохраняет доступ» — бизнес-решение; при другом правиле меняется одна ветка в `RefundSucceeded`.
- Попытка, которую провайдер не может создать, остаётся в `Creating` и повторяется каждый цикл; срока отказа нет.
- Хэш тела считается по сырым байтам: если провайдер повторно отправляет событие с изменённой сериализацией, оно будет сочтено конфликтом.
- У админ-эндпоинтов нет авторизации.
- Тесты делят одну БД и один процесс и идут последовательно (одна коллекция xUnit); тесты таймаута занимают секунды.
